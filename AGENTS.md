# TripShare engineering rules

- Trip planning and Money are independently navigable. Planning estimates, templates, capacity and waiting lists must never post consumption or repayments. A supplier bill marked Paid updates its original expense ID and incurred date. Money conflict recovery stays scoped to Money.
- The user has deferred time polls and RSVP. Do not add AI, OCR, voice parsing or calendar write permissions as incidental scope.
- Preserve the approved hybrid layout and the three complete light/dark themes. Keep secondary views focused and paged, using existing tokens. Show samples before proposing a different overall design.
- Only server-verified permissions authorize writes. Trip private preferences belong in their separate table and API; only their author and the trip owner can read them. Never put them into shared group JSON, public links, templates, calendar exports or offline packs.
- After each requested implementation, review correctness, authorization and cross-group isolation, concurrency/idempotency, compatibility, error recovery and the first likely performance bottleneck. Fix release blockers before publishing. Record concrete non-blocking improvements instead of adding speculative features automatically.
- Update `docs/engineering-review.md` with the shipped scope, tests, known limits and the verdict: KEEP / CHANGE NOW / IMPROVE LATER / DO NOT ADD. State unavailable verification explicitly. Do not claim an actual device, browser or external calendar test from SSR/unit checks.
- Use the Sites workflow to open, package and publish the existing project. Keep source credentials in session memory and retain current site audience. Schema migrations are additive, generated through Drizzle, and applied through Sites publication. Never rewrite applied migration history.

- Before any visual redesign, present multiple concrete samples and wait for the user's selection. Functional corrections can proceed using engineering judgment; ask when behavior or scope is materially ambiguous.
- The user's latest 2026-10-20 request supersedes the v57/v58 reduced-navigation designs: restore the v56 full Admin navigation and detailed interfaces first, then stop at that baseline. Keep Trip and Money independent: Trip covers the complete journey and linked costs; Money handles trip bills and everyday groups. Preserve the concise member itinerary, personal-only Money, backend permissions, all three light/dark themes and saved preferences. Future entry-point reductions must be small, incremental and reviewed with the user; do not perform another broad regrouping or remove detailed functions without selection/confirmation.
- The subsequent screenshot-specific request authorizes only this first incremental cleanup: move New Trip into the top-level workspace area; remove the duplicate floating Today / Tickets / + Plan strip; keep travel tools inside one collapsed, explained Trip tools menu; expose one contextual Add plan / Add booking entry per planner page while retaining all plan types and detailed forms. Keep every full Admin page in navigation. Use the previously selected mist-violet light palette without resetting saved themes. Responsive layout follows CSS viewport width and safe areas, not physical phone inches; never claim real-device coverage from CSS/SSR tests.
- The next approved cleanup removes the planner's duplicate Trip costs/Open itinerary links; keeps contextual Coming up rows; displays Trip Plan as Overview and Admin Simple itinerary as Preview member view while preserving internal destination IDs and member routes. Overview uses a short, permission-scoped financial summary; full cost operations stay in Trip costs. Trip details holds essentials/settings; daily lists stay in Itinerary. Hide empty task metrics/attention panels and repeated Trip context captions. Preserve the established palette and detailed functions.
