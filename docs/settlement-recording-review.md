# Selected-bill and batch settlement — 26 October 2026

## Selected scope and current flow

The user selected proposal items 1–6, 9 and 11–13, excluding search (7), additional owe-me/I-owe filters (8) and remembered dates/methods (10). The preceding four-point request replaces lifetime Calculation detail with unpaid source detail and the inline payment editor with one centered dialog. Existing Mine/Everyone, Money/Trip separation, themes, personal links and server permissions remain intact.

Settlement now groups current transfers by recipient in collapsible sections, offers a bill filter and explicit pair/group selection, and copies the visible recipient list without sending messages. Recording opens a bounded dialog with a scrolling body and always-visible footer. Each pair independently selects one or more current payable source bills, automatically totals them, and permits a smaller cash amount plus its own date/note. Partial cash applies in the displayed source order. The available amounts are **after** existing repayments and reciprocal offsets, so an offset portion cannot be recorded as cash again. Per-source original/applied/available information and partial statuses explain the cap. Source bill selection is separate from consumption-item editing.

Calculation derives residual source amounts from canonical pair source obligations and applied source cash, excludes cleared sources and old cash-allocation history, and shows only current opposite obligations/offset/remaining. The existing Past payments/audit records retain history; review warnings remain for unmatched money. Summary/print/CSV behavior from the prior release is preserved.

## Server mutation boundary

`lib/settlement-recording.ts` validates up to 100 unique member pairs and payment identities, positive safe-integer amounts, dates/notes and unique selected source IDs. One canonical ledger replay supplies a source index. Allocations are computed **server-side** from current net payable claims belonging to the requested pair and selected bills. Client allocations are ignored. Multiple rows for the same unordered pair, unknown sources/people, overpayments, self-payments and reused identities are rejected.

`paymentBatch` checks current authenticated group permission before idempotency. An exact already-applied batch returns success before the stale-revision guard; changed details/source choices, an undone batch or reused identities fail. Each payment stores optional `batchId` and `selectedExpenses` alongside its immutable actual allocations. A single existing group revision/CAS + D1 transaction writes the complete event, one audit entry and per-payment scoped sync changes. A bad row saves nothing; concurrent submissions have one winner; a failed sync insertion rolls back the group update. No database schema/dependency/hosting audience change is needed.

Batch Undo marks the original payments reversed and retains records/allocations/audit. It checks settle permission and revision, updates scoped sync tombstones atomically, and is retry-safe when already reversed. Individual history Undo remains compatible. Ordinary members still receive only their authorized personal payment projection and related source titles.

## Client recovery and feedback

The dialog prevents duplicate clicks and editing while a request is running. A timeout, network loss, invalid successful response or 5xx freezes the exact batch IDs/details/revision; retry checks that same intent instead of creating payments. Confirmed conflicts save nothing and retain the selection; current amounts must be reviewed, changed source choices are reconciled and fully settled rows can be removed before retry. Success shows each saved pair, count and total, with immediate Undo and explicit reversed results. Closing returns to the captured page position. Permission loss cannot authorize a retry; the user is directed to verify earlier uncertain history with the owner. A confirmed save with failed refresh remains labeled saved and requests refresh before another payment.

## Verdict

- KEEP: source-bound replay, pairwise original-creditor netting, integer money, original expenses/payers, recorded cash/history, server group authorization, personal isolation, CAS, sync identity and all three themes. The new optional JSON fields are backward compatible; rolling back UI/API code leaves allocations replayable and individually reversible by the old controls.
- CHANGE NOW: selected-source server validation, atomic batches, exact retry semantics, current-only Calculation, recipient/bill organization, individual partial amounts, explicit receipts and a bounded mobile confirmation dialog. Private payout details render once per recipient rather than repeating the same request per debtor.
- IMPROVE LATER: physical handset keyboard/safe-area behavior and native printer validation are not covered. Unconfirmed request identity is retained in the current mounted dialog, not a durable offline queue; after a forced page reload users must check current history before manually creating another payment. Existing whole-event JSON validation/ledger replay is the first likely backend bottleneck; frontend source indexing is linear and a very large selected batch can still grow a long dialog. Measure before virtualizing or changing storage.
- DO NOT ADD: search, new personal-direction filters, remembered payment method/date, automatic paid status, preselected whole-group payments, creditor rerouting, automatic financial messages, an offline submission queue or another accounting ledger.
